# SR-01 through SR-05 review and verification

Reviewed actual `main`, starting at `e85262144601234f0a912a680345f9b492386581`.
The worktree was clean and fetching upstream found no newer commits. This
report covers only SR-01 through SR-05. No permanent tests were added.

## SR-01: Prometheus forwarding

**Confirmed and fixed.** Previously `Response::bytes()` allocated the entire
upstream response before returning it. In particular, the range endpoint had
no useful body-size bound.

The response now connects reqwest's byte stream directly to Axum's response
body, without a producer task, channel or whole-response allocation. Downstream
backpressure controls upstream polling. Buffering consists of bounded protocol,
chunk and socket buffers, independent of the total response size. There is no
new query/body-size restriction. The same three read-only routes, `no_proxy`,
disabled redirects, 30-second request timeout, upstream HTTP status and JSON
content type remain. Page/chart code and health behavior are unchanged.

A send failure before headers still returns a fixed 502. A body/read failure
after headers terminates the stream, so a caller receives a truncated response
rather than a replacement JSON error. The implementation documents this. Raw
upstream errors are logged, never inserted into the forwarded response.

A temporary local fake Prometheus streamed JSON without retaining its full
body. A separate HTTP client drained the real `homestack-usage` binary while
sampling its `/proc/<pid>/status` RSS:

| Case | Body bytes | Peak service RSS (KiB) |
| --- | ---: | ---: |
| Startup baseline | — | 30,036 |
| Small normal JSON | 16 | 30,192 |
| Large JSON | 16,777,216 | 31,416 |
| Much larger JSON | 268,435,456 | 31,416 |
| Slowly produced JSON | 131,072 | 31,416 |
| Non-200 JSON (422) | 16 | 31,416 |

The 256 MiB response had the same peak RSS as the 16 MiB response, about
1.35 MiB above baseline. Slow-upstream headers arrived in 4 ms, before its
403 ms body finished. With the consumer paused for a second, upstream sending
stalled after 8,126,473 bytes, with service RSS still 31,416 KiB. This includes
kernel socket buffering on both sides; it is not an 8 MiB application queue.
A premature upstream disconnect was detected as a truncated transfer. An
unavailable upstream returned 502 while readiness stayed 200. All three
allowlisted routes worked; four other Prometheus paths returned 404 and POST
returned 405.

Release impact: AI-usage image.

## SR-02: plans, jobs and event collections

### Plans — confirmed and fixed

Previously, there was **no cardinality bound** within the default 15-minute
TTL. Authentication and the 64 KiB plan/apply request limit bounded individual
inputs but did not limit the number of stored plans. Repeated planning of the
same target was sufficient; no VM allocation was needed.

There are now **at most 128 unapplied plans per server instance**. Excess
creation returns deterministic `409 busy`; reviewed, unexpired plans are never
evicted to admit another. Expiry is still pruned whenever state is locked.
128 drafts allow many alternatives per installation without retaining thousands
of 64 KiB parameter documents. This is an internal limit, not another setting.

An applied plan is removed immediately. The intentional contract adjustment is
documented in the handlers and regenerated OpenAPI: GET of an applied plan
returns 404; repeat apply returns `plan_applied` while its job is retained,
then 404. Jobs retain the plan ID. Unapplied plans remain valid until their
original expiry, subject to the existing digest/configuration checks.

### Concurrent jobs — partially confirmed and fixed narrowly

Previously there was no explicit job admission bound. All built-in operations
have one target; the generic operation model supports several. `busy` enforces
one active operation per target and leases coordinate existing VMs across
instances, but neither limits the number of independent targets. A nonexistent
create target cannot yet carry a PVE lease. Pool membership is an authorization
boundary, not a small cardinality cap. Proxmox's VMID namespace (100 through
999999999, or 999999900 possible IDs) is finite but not a useful memory bound;
workspace addressing narrows creation further, while power operations can act
on existing pool targets. The exact old running-job ceiling depended on cluster
inventory and available creation targets, not `retained_jobs=100`.

There are now **at most 32 admitted applies/jobs per instance**, including
replanning and lease acquisition. A semaphore permit is acquired before local
target locking or any lease write; refusal returns `409 busy`. A guard releases
the permit and local target locks on errors or cancellation, and remains owned
by the spawned operation until completion. Admission is per operation, including
multi-target operations, not per VM. Existing per-target busy checks remain.
32 permits provide substantial parallelism across a HomeStack cluster without
launching hundreds of simultaneous Proxmox workflows.

Every active job remains retained. Completed retention is independently
**max(1, retained_jobs)**, default **100**, trimmed on insertion and completion.
Thus the default job map has at most **132 jobs** (32 active + 100 finished),
newest first. Old code only tried to reduce total length to 100 at insertion,
removing finished jobs; active jobs could exceed it, and later completion did
not itself restore that nominal count. No running sender is evicted.

Temporary diagnostics exercised 128 plans, refusal of the 129th, preservation
of an old reviewed plan, expiry and capacity recovery, and recovery after apply.
They held 32 simultaneous **two-target** diagnostic operations, confirmed the
33rd refusal made **zero PVE calls**, kept an active watch receiver through
completion, and then checked three retained finished jobs with a diagnostic
retention setting of three. Previously refused targets and released targets
subsequently admitted work. Log input of 250 lines retained exactly the newest
200. No diagnostic operation performed PVE mutations.

### Steps/tasks — inaccurate as a claim of indefinite accumulation

No truncation was added. All `StepStarted` producers are the fixed lifecycle
helper and `JobHandle::step`; built-in operations use the former. The longest
built-in step sequence is create with cross-node migration: nine steps. Refresh
has seven replacement steps or one explicit recovery step, resize three,
addkey four, migration at most six ordinary plus one recovery step, destroy
two, and power one. Before/after step bounds are unchanged.

The sole `TaskStarted` producer is entry to `wait_task_tracking`, called through
finite internal submission workflows, including power, clone, config updates,
resize and migration. Polling task status/log pages emits log/progress events,
not additional task starts. Retrying lock failures can add tasks, but retries
have a 120-second deadline and, with production timing, a five-second pause:
at most 24 attempts per retrying submission. The total task bound is the finite
number of workflow submissions multiplied by this retry bound, plus nonretrying
submissions; it is unchanged by this batch. There is no client-provided list of
steps or tasks and no workflow that creates one task per arbitrary log line,
metric, input key or inventory entry. Custom Rust `Operation` implementations
are trusted application code, not a remotely supplied workflow language.

`Job.log` remains capped at **200 lines**, before and after.

Release impact: API image.

## SR-03: public Proxmox errors

**Confirmed and fixed.** Synchronous HTTP errors and `JobError` now use the
same `public_pve_error` code/message mapping:

| PVE variant | Public code | Fixed public message |
| --- | --- | --- |
| Unreachable | `pve_unavailable` | No Proxmox API endpoint is reachable. |
| Unauthorized | `pve_auth_failed` | Proxmox rejected the server's API token. |
| Forbidden | `pve_permission_denied` | The server's Proxmox API token lacks a required privilege. |
| NodeUnreachable | `pve_node_unavailable` | Proxmox could not reach the requested node. |
| Api / Response | `pve_error` | Proxmox returned an error or an unusable response. |
| Config | `internal` | The server is misconfigured. |

Inspection also found lifecycle recovery helpers flattening typed PVE failures
into ordinary `Failed` strings. They now preserve typed causes alongside the
existing detailed display message, allowing the same sanitization to recognize
nested failures. This preserves CLI recovery descriptions and the existing
operation/recovery behavior. Guest-agent checked failures retain their causes;
the addkey success note no longer embeds a raw ping failure. Its detail is logged.
Non-PVE validation, busy and outside-pool messages keep their existing policy.
The read-route error match handles the new contextual variant with its existing
fixed unusable-data response.

Temporary diagnostics injected all seven PVE variants both directly and with
recovery context into synchronous plan failures and running job failures.
They compared HTTP error bodies with GET /v1/jobs and actual WebSocket frames.
Sensitive-looking sentinel endpoint/transport/response strings were absent from
all public captures. Operator warning captures contained the original detailed
errors, including contextual causes. HTTP request logs still use route templates
rather than raw paths or headers. Token and Editor Debug remain redacted.

Release impact: API image (including shared hs-core/hs-pve changes).

## SR-04: CI and destructive-test reliability

### API immutability/platform/provenance — confirmed and fixed

Numeric API image tags now refuse an already published artifact. A shared
admission helper treats registry/auth/network failures as errors rather than
permission to publish. Publication is serialized per component/tag (dev builds
per component/SHA). The build explicitly uses `linux/amd64` and
`provenance: false`: PVE OCI pulls receive one deployable runtime manifest,
without an attestation index. Numeric versioning and tag helpers are unchanged.

### Same-SHA dev reruns — partially confirmed and fixed narrowly

One immutable `dev-<commit>` artifact per component is intentional; failing
an otherwise valid repeated dispatch is unnecessary. Existing dev artifacts now
skip build/validation/push successfully only after checking single-manifest
shape, pulling the image (which validates its blobs), checking linux/amd64, and
matching source, component title, revision and version labels. Incorrect or
unverifiable artifacts fail closed. Existing numeric releases always refuse
publication. Dispatch still intentionally launches all three dev image jobs;
the workflow UI and release numbering were not redesigned.

The helper passed 32 mocked missing-tag, existing-release, valid-dev,
wrong-revision, wrong-component, wrong-platform, index and authorization cases
across the four image repositories. No mock check performed publication.
Workflow YAML assertions, actionlint 1.7.7 and ShellCheck 0.10.0 passed.

### Production topology live gate — confirmed and fixed; live run unavailable

Previously the script built the bare final stage and called HTTP :8080. It now
builds `--target node` unless `HOMESTACK_IMAGE` supplies an image. Both local and
supplied images must run the normal runit entrypoint, homestack service and
Caddy. The gate checks both supervised services and calls all API routes through
Caddy's :443 front door with a temporary CA-signed localhost certificate and
curl certificate verification enabled. Port 80 is checked for management health
and 404 on representative API/config/secret paths. Production TLS configuration
was not modified. PVE failover and configuration-volume replacement checks remain.

Host fixture files remain private. A short root initializer installs the two
run-owned token files with mode 0600 for the image's homestack account. TLS
bootstrap uses a private environment file. The fixture/container/volume are
removed on exit. There are no additional PVE mutations.

Docker is not installed in this development environment, so the actual image
build/runit/Caddy/PVE live gate was **not executed**. Shell syntax, ShellCheck
and code review are evidence of the script change, not production-topology
runtime evidence. The exact temporary certificate-generation block was also
executed locally: OpenSSL verified its CA chain for both localhost and 127.0.0.1,
and fixture key/environment modes were 0600. Full isolated E2E and real PVE tests were intentionally not run.

### Capacity cleanup — confirmed and fixed

Cleanup now attempts server stop, each guarded Gold/bridge/storage ACL removal,
the owned storage object, the exact tmpfs mount and `super().cleanup()` despite
earlier exceptions. Failures are combined in an ExceptionGroup after all
attempts. If verification also failed, BaseExceptionGroup preserves both.
Ownership booleans, exact paths, token/role selectors and fixture scope remain.
Seven injected-failure diagnostics confirmed every later cleanup step ran;
separate checks covered false ownership guards and combined verification/cleanup
failures. No real owned or unrelated infrastructure was deleted during diagnostics.

SR-04 changes alone need no runtime image/package release.

## SR-05: best-effort memory hygiene

**Defense-in-depth only.** The Editor Debug leak claim is **stale/already fixed**;
its custom redacted Debug was preserved. PveToken Debug, secret parse-error
messages and sensitive Authorization header marking were already intentional
and remain intact.

PveToken's secret is now `Zeroizing<String>`, including every clone. Its file
read buffer and complete temporary `PVEAPIToken=...` representation are also
zeroizing. No unsafe HeaderValue/reqwest memory manipulation was added.

Editor original documents, current values and saved-value snapshots now use
zeroizing wrappers. A whole zeroizing vector avoids introducing a mixed-field
secret abstraction while also wiping cloned worker editors. Serialized documents,
serialization line buffers, TSIG token vectors, sanitized-error intermediate
buffers and edit/paste character buffers are zeroizing. Explicit clear/replacement
wipes the previous edited string. Masking, validation, clipboard scope, private
atomic save and non-secret Settings summary/report content are unchanged.

Temporary sentinel diagnostics checked both custom Debug representations,
public parse errors, error redaction, cloned wrapper types, serialization,
unicode paste/backspace/clear behavior, saved file mode 0600 and absence of
credentials from Settings/summary output. They do not claim a forensic proof
of complete erasure.

The practical boundary is explicit: HTTP/header/TLS library buffers, allocator
reallocations and prior copies, terminal render buffers, parser temporaries,
external clipboard/process memory and downstream provider-client credential
objects cannot all be guaranteed to be wiped. Existing hs-deploy OVH/Spaceship
credential structs were inspected and left as residual hardening; this batch
does not recursively redesign provider clients. No credential summary/cache
was introduced and no credentials are logged by the token/editor changes.

Release impact: API for hs-pve; TUI hardening alone has no image impact.
