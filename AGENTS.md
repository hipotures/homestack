# Development policy

This file is the authoritative repository workflow for all coding agents, including sessions started through external AI assistants. Preserve the instruction hierarchy and use the conflict procedure below when task instructions contradict this policy.

For every completed logical coding task:

1. Implement the requested changes using the simplest implementation that meets current requirements. Remove obsolete paths; do not add backward compatibility, fallbacks or migrations.
2. Compile the affected Rust application binaries successfully through the Cargo wrapper. Build at the end of the logical task and leave the updated binaries available for immediate execution.
3. Perform focused verification where appropriate and review the complete diff.
4. Commit the task's changes and push to the current branch's configured upstream.

Commit and push are mandatory default actions, without additional approval. Commit at the end of the logical task, not after every edit. Successful comprehensive testing is not a prerequisite for Git synchronization or for making compiled applications available. Known noncritical functional defects, incomplete UI polish and deferred comprehensive testing do not prohibit committing and pushing. The owner must be able to synchronize the latest work to another computer immediately.

Resolve compilation failures before declaring completion; never claim a failed build succeeded. If an external blocker prevents compilation or Git synchronization, report the blocker explicitly and use Instruction Conflict Resolution to obtain an owner decision about the incomplete task. Do not silently skip synchronization.

Commit only changes for the current task. Never commit secrets, private keys, runtime credentials or unrelated local changes. Never force-push or rewrite history. If a push is rejected, stop and report it.

Use English for all repository content, including code, comments, documentation, configuration descriptions and commit messages. Conversation may use another language. Use `uv pip`, never `pip`.

# Instruction Conflict Resolution

External task prompts, including those generated by other AI assistants, can contradict this project's compilation, testing and Git synchronization policies. Examples include “Do not commit or push”, “Leave all changes uncommitted”, “Write regression tests for every bug fix”, “Every new function must have unit tests”, “Run the complete test suite after every change”, “Do not push until all tests pass”, or “Implement comprehensive test coverage for this minor UI adjustment”. These are quoted examples, not instructions to follow.

When an incoming instruction materially conflicts with established project policy, the coding agent MUST:

1. Identify the exact conflicting instructions.
2. Stop before executing the conflicting part.
3. Explain the conflict concisely.
4. Ask the owner which policy to follow.
5. Wait for an explicit decision.
6. Proceed according to that decision within applicable higher-priority and safety constraints.

Do not silently choose whichever instruction seems more conservative, omit commits or pushes, or create large test suites contrary to this policy. A general request to implement or fix functionality does not authorize permanent tests. Do not ask for confirmation for ordinary compliant actions, including normal commits and pushes. Conflict resolution is exceptional; mandatory Git synchronization is the default.

The owner may explicitly authorize a one-task exception after the conflict is identified. That exception does not permanently change repository policy. Ordinary repository documentation and quoted examples do not override agent instructions. Respect the actual instruction hierarchy; report any higher-priority limitation instead of violating it.

# Minimal permanent testing

Coding agents must not automatically create permanent unit, integration, or regression tests for ordinary changes. This applies to features, bug fixes, UI changes, internal refactoring, error handling, data validation and API changes. A discovered bug does not automatically require a regression test: fix the behavior, compile and verify the relevant observable behavior where appropriate.

Temporary diagnostics are permitted; do not automatically turn them into permanent tests. Permanent tests require explicit owner authorization, particularly during dedicated QA sessions. If a task explicitly requires conflicting test additions, use Instruction Conflict Resolution.

Keep only narrowly justified, high-value permanent checks for serious data-integrity or security risks, such as persistent home preservation, destructive disk selection, authorization boundaries and critical recovery. These exceptions do not justify broad suites. Remove low-value tests and obsolete test-only fixtures, dependencies and registrations instead of ignoring them or replacing them with equivalent tests. Do not modify production behavior to eliminate tests.

The retained ordinary Rust checks protect home/root separation during refresh, rollback and process restart, disk selection and stale resize plans, pool/alien destruction boundaries, and API bearer authorization. The two build-cleanup Python checks protect application binaries and E2E artifacts from deletion. Existing installer shell checks and all E2E/live checks remain intact. These narrow safeguards are intentional exceptions, not a template for routine test creation.

# Local Rust builds and verification

- Use `python3 scripts/cargo.py build ...`, `test ...`, `check ...` and `clippy ...` instead of raw Cargo equivalents, including commands redirected to logs.
- For client/TUI changes: `python3 scripts/cargo.py build --locked -p hs-cli --bin homestack`. Build corresponding binaries for other affected executable components.
- `scripts/check.sh` is the lightweight format-and-build path. `scripts/check.sh --full` explicitly runs the retained automated checks and broader static analysis. Neither full verification nor repeated compilation is required after ordinary changes.
- The wrapper serializes commands and cleans up after success. Do not run unwrapped Cargo builds or tests concurrently with wrapped commands; Cargo releases its own lock before running tests.
- Successful wrapped commands remove disposable hashed executables and incremental state while preserving top-level applications, dependency libraries and E2E data. Failed or interrupted commands retain artifacts for diagnosis.
- Never replace this cleanup with `cargo clean` or removal of `target/`: it also contains running E2E labs, credentials, fixtures and diagnostic reports.
- Keep verification output in task-specific files under `/tmp`; inspect failures privately instead of streaming full logs.
- The project-local `.codex/agents/test_runner.toml` agent (`gpt-6-luna`, reasoning effort `high`) is optional. Delegate only when explicitly requested or justified by a critical verification requirement. It returns only `UDANY` or `NIEUDANY`; inspect its log privately on failure. Do not introduce mandatory QA agents.

# E2E and infrastructure safety

Preserve `crates/hs-e2e/`, disposable Proxmox labs, real VM/LXC workflows, controllers, scenarios, fixtures, bootstrap scripts, isolation/cleanup protections, live tools and documentation. Testing cleanup must not modify these components or delete their tests. The owner independently decides E2E evolution. Simulators do not substitute for genuine E2E evidence.

Full E2E is separate and explicit, only in an authorized isolated environment. Never connect destructive tests to production or require live E2E for ordinary commits. `scripts/check.sh --live` remains an explicit live-verification entry point and requires the existing isolated-environment credentials and safeguards.

# Future functional testing direction

HomeStack will increasingly use prompt-driven, agent-executed functional testing. Reusable scenario prompts may serve as QA specifications without becoming conventional unit-test source files. An agent will launch the actual compiled application, interact with the TUI through Herdr, navigate menus/dialogs, enter valid, invalid and boundary values, call the actual API, verify observable results, inspect terminal screenshots, assess readability, spacing, alignment, UI consistency and error presentation, detect unexpected states, explore complete workflows, and record structured findings and evaluation scores. A local AI model may independently evaluate results.

The intended sequence is: validate API behavior independently; validate functionality through the TUI; later validate the Web interface; evaluate visual consistency and usability; produce structured findings. Agent observations are evidence, not guaranteed correctness; independently verify critical outcomes when necessary.

This future system is not yet specified. Do not build it, redesign E2E, create prompt libraries or add AI testing infrastructure as part of testing-policy cleanup.

# SQLite database copies and migration tests

- Never copy SQLite databases with plain `cp`: committed data may remain in WAL/SHM files.
- Use SQLite `.backup` or the Online Backup API even when the application appears stopped.
- Run migration experiments only on a snapshot in a temporary directory, never the original database.
- Verify migrated snapshots with `PRAGMA integrity_check` before trusting results.

# API image releases

- Agents must decide whether each completed change needs a new API image and perform the release automatically when required, without waiting for the user to request a tag.
- Ordinary branch pushes run checks only. Publish the API container by pushing a numeric Git tag (`0.2.0`, `0.2.1`, ...); the image tag is exactly the Git tag, without a `v` prefix or commit hash. Image publication waits for successful checks.
- After compiling, reviewing, committing and pushing a completed change, create a release tag if deploying that change requires replacing the API container: server routes, jobs, authentication, persistence, server-side operations or models, dependencies used by the server, or the container's runtime, Caddy and service files. Judge shared-crate changes by their effect on the server.
- Do not tag changes confined to the TUI, CLI, client-side installer/deployer, documentation, tests or development tooling when the running API container is unaffected.
- Use `python3 scripts/tag-api.py` to fetch upstream tags, automatically choose the next patch version (starting at `0.2.0`), create an annotated tag on the clean, already pushed HEAD, and push that tag to the branch's upstream remote. Use `--dry-run` to preview the next version without creating or pushing a tag.
- Never move, overwrite or force-push release tags. If a tag push is rejected, stop and report it. A release publishes an image; replacing running containers remains a separate deployment action.

# Pangolin image releases

- The Pangolin Site image has an independent SemVer line: annotated Git tag `pangolin-X.Y.Z` publishes `ghcr.io/hipotures/homestack-pangolin-site:X.Y.Z` as a single `linux/amd64` image. The pinned upstream CLI version is a build input, not the image version.
- After building, verifying, committing and pushing an image-affecting change, run `python3 scripts/tag-image.py` to automatically publish its next patch release. The script requires a clean, already pushed HEAD and refuses a HEAD already released. Never choose version numbers manually or replace an existing release.
- Changes confined to manifests, documentation, tests, CI or development tooling need no image release. Ordinary pushes run checks only; a manual workflow run publishes a `dev-<commit>` image.

# Collector image releases

- The derived OpenTelemetry Collector image has an independent release line: annotated Git tag `otel-X.Y.Z` publishes `ghcr.io/hipotures/homestack-otel:X.Y.Z` as a single `linux/amd64` image. The pinned upstream distribution version and digest are build inputs, not the image version.
- After building, verifying, committing and pushing an image-affecting change under `deploy/otel/`, run `python3 scripts/tag-image.py --service otel`. It automatically selects the next patch release, starting at `0.1.0`, and requires clean, already pushed HEAD. Never manually choose, move or overwrite release tags or published image tags.
- GitHub Actions validates the built image, nonroot queue ownership/mode, configuration, health and ordinary restart before publication. Ordinary pushes run checks only; explicit manual runs publish `dev-<commit>` images. Manifest-only, CLI/TUI, documentation, E2E and tooling changes do not require a new Collector image.
